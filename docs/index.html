About this demo

A cluster of servers keeps data consistent by electing one leader. The leader sends a heartbeat to every follower every 100 ms. Each follower runs a countdown, the election timeout, drawn at random between T and 2T. If no heartbeat arrives before the countdown ends, the follower starts an election. While there is no working leader, the service is down.

A short timeout replaces a failed or slow leader quickly, but late heartbeats caused by network jitter trigger unnecessary elections. A long timeout avoids false alarms but makes real outages longer and lets slow leaders stay in charge. This page runs the same model as the notebook, so you can find the timeout that gives the least downtime.

How to use

  1. Press Start to watch one run. Use Speed to go faster, and Pause to stop and look.
  2. Move a slider (for example the timeout T or the jitter m). The run restarts with the new setting.
  3. Click a node to make it slow or failed and watch the others react.
  4. Under Check against the notebook, press Run replications for an average with a 95% confidence interval, or Reproduce notebook row to repeat a whole row of the notebook's main sweep.
  5. Reset clears the run and starts again from time 0.

Reading the picture

  • Leader, candidate, follower
  • Ring colour = health: healthy, slow, failed
  • Thin grey arc = time left on a follower's election timer
  • Moving dots = messages: heartbeat, vote request, vote reply
  • Bottom strip of the chart: healthy leader, slow leader, no working leader

Downtime

Weighted downtime = time with no working leader + w × time with a slow leader, shown as a % of the simulated time. With w = 0 a slow leader costs nothing; with w = 1 it counts like no leader.

Reference result and tolerance

Press Load notebook reference setting (late messages, exponential jitter m = 20 ms, T = 200 ms, s = 300 ms, w = 0.5, 5 nodes), then Run replications with 30 runs of 10 minutes and seed 0. The demo gives 0.40 ± 0.11 % downtime. The notebook (section 6.3) gives 0.43 ± 0.20 %. The check passes when the two means cannot be told apart by a 95% Welch interval, the same test the notebook uses. The page uses a different random-number generator from NumPy, so the numbers are close but not identical. That is why a tolerance is needed.

Limitations

  • Timing only: no log replication, no message loss and no network partitions, as in the notebook.
  • The health transition matrix, s and w are illustrative values, not measurements from a real cluster.
  • Notebook reference values exist only for the main-sweep settings (T = 150 to 3000 ms, m = 5, 20 or 50 ms, s = 300 ms, w = 0.5, 5 nodes, 10-minute runs).
